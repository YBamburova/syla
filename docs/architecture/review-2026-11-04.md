# Architecture readiness review

Date: 2026-11-04. Status: review findings and recommendations; no new architecture decisions accepted.

## Assessment

The product direction and system boundaries are sufficient to plan implementation. They are not yet sufficient to implement workout scoring, authorization, or cross-module workflows consistently. The next investment should be concrete examples and a small runnable slice, with documentation added around it.

This review assesses the repository's vision, arc42 sections 1–4, ADRs 0001–0011, C4 workspace, and development instructions. There is no application code to verify. Provider capabilities, comparative market claims, legal conclusions, and current library compatibility were not externally validated; those require targeted research when their decisions are prepared.

Preserve: Java core as system of record; Python proposals requiring human confirmation; manual fallback; athlete-owned workout copies; modular boundaries; explicit privacy requirements; Docker Compose demo. No stack replacement is recommended by this review.

## Findings and decision backlog

Priority indicates when work is needed, not that every finding requires a new ADR. Product behavior belongs in specifications; consequential technical decisions belong in ADRs. Milestones refer to the [proposed delivery plan](../milestones.md).

### R1 — Workout and score semantics are the first domain blocker

**Evidence:** [F1–F3](01-introduction-and-goals.md) name formats and progress features; [ADR-0004](../adr/0004-postgresql-with-pgvector.md) chooses tables and JSONB but does not define the domain contract.

**Risk:** manual entry, AI parsing, classes, ranking, and progress could each invent a different workout representation.

**Before M1:** specify session versus section versus result; prescribed movements versus performed movements; strength sets, decimal loads, kg/lb handling; AMRAP rounds plus reps; completed versus capped For Time; EMOM/Tabata results; RX/scaled; missing results; local training dates. Decide edit/delete behavior and distinguish a named benchmark from an arbitrary workout with the same name.

**Recommendation:** agree on a compact fixture set covering strength, AMRAP, completed and capped For Time, EMOM, Tabata, and a mixed strength/metcon board. Label which examples ship in M1 and which extend the model in M2. Use the same fixtures across API, UI, parser, and progress tests. Do not require every format in the first demo.

### R2 — Identity, authorization, and visibility need a shared policy

**Evidence:** authentication is open in [strategy §4.3](04-solution-strategy.md); [ADR-0010](../adr/0010-gym-classes-and-co-attendance.md) defines gym visibility and says hidden class scores follow normal feed visibility, which is not yet defined.

**Risk:** a hidden class score or private gym activity can be exposed through a feed, profile, export, or API query. Hiding a score is explicitly not a global privacy setting under the current ADR; the UI must explain this.

**Before M1:** authentication ADR covering local and future deployment, identity mapping, session/token lifecycle, browser protections, and account deletion. Define ownership checks on every workout operation. Recommend private personal history for the first demo, pending explicit specification.

**Before M3/M5:** permission matrix for owner, gym member, nonmember, admin, and follower; profile/workout audiences; private gym references in feeds; hidden-score behavior in every response; membership removal and visibility changes. A change to ADR-0010's publication rules requires a new ADR accepted by the user.

### R3 — Module boundaries need transaction and recovery examples

**Evidence:** [ADR-0002](../adr/0002-modular-monolith-core.md) prohibits cross-schema foreign keys and joins; [ADR-0010](../adr/0010-gym-classes-and-co-attendance.md) separates attendance and workouts; [ADR-0006](../adr/0006-rabbitmq-for-async-messaging.md) requires reliable publication and idempotent consumers.

**Risk:** retries create duplicate workouts or attendance; a partial failure leaves dangling records; deletion followed by event replay restores deleted data. The generic instruction that everything outside a waiting request is async does not define atomicity within the core.

**Before M1:** document workout save/edit/delete and internal event publication, including transaction boundaries. **Before M3:** design attendance creation and duplicate submissions; choose public module APIs/events without accessing internals; document rollback or compensation and reconciliation. **Before any AMQP consumer:** message envelope, versioning, deduplication identity, retry limits, dead-letter handling, and replay policy.

**Recommendation:** add runtime sequences for success, retry, and failure. Verify outbox behavior with the selected Spring versions before promising delivery guarantees. Do not add an unused async insights feature merely to exercise RabbitMQ.

### R4 — Privacy workflows must expand with each feature

**Evidence:** [vision §7](../vision.md) and [strategy §4.2](04-solution-strategy.md) require consent, export, and deletion; ownership is distributed across modules.

**Risk:** an account disappears while events, derived progress, provider tokens, comments, or published class attribution remain identifiable.

**Before M1:** inventory personal data, consent records where required, export format, deletion orchestration, failure/retry behavior, and retention categories. Add a small threat model with trust boundaries and principal abuse cases. Extend these artifacts in every later milestone.

**Before M2:** define external-AI disclosure and controls, and redact/minimize text input as well as images. **Before M6:** address provider revocation, in-flight imports, token storage, backups, and operational retention. This review does not establish legal compliance; the documents' legal and provider assumptions remain validation items before real-user launch.

### R5 — AI quality targets need a reproducible evaluation contract

**Evidence:** [quality goals](01-introduction-and-goals.md) set 90% accuracy and latency targets; [ADR-0009](../adr/0009-whiteboard-photo-parsing.md) requires a shared text/photo schema and process-and-discard images.

**Risk:** “exact match” penalizes harmless ordering while missing dangerous unit errors; mocks are mistaken for real-model accuracy; request middleware or proxies spool image uploads to disk despite application code using memory.

**Before M2:** define canonical comparison, critical fields, ambiguous/unreadable inputs, unsupported workouts, and the human correction flow. Version a permissioned dataset and hold-out cases. Report text and photo results separately with sample counts, model/prompt versions, latency measurement boundary, and cost. Keep deterministic CI tests separate from credentialed live evaluations.

**Recommendation:** reject invalid structured output; never invent a missing load or score. Enforce server-side size/type limits and inspect upload buffering, proxy logs, telemetry, and caches. Client EXIF stripping alone is not a complete enforcement boundary. Include request limits and parser abuse controls. Retain the current latency/accuracy targets until measured evidence supports a user-approved revision.

### R6 — Gym results need fair comparison and lifecycle rules

**Evidence:** [ADR-0010](../adr/0010-gym-classes-and-co-attendance.md) ranks within RX and scaled, preserves old workout copies after class edits, and transfers admin to the longest-standing member.

**Risk:** incomparable scaled results or different template revisions appear in one ranking; concurrent publications create duplicates; the last admin has no successor in an empty gym.

**Before M3:** define class revision identity, movement/load equivalence, ties, capped results, optional time-slot uniqueness, attendance cancellation, repeated logs, and what happens when a gym has no members. Clarify authorization after a publisher leaves, invite expiry/revocation, and concurrent joins. Recommend no shared rank where results are not comparable; obtain agreement on product behavior before coding it.

### R7 — Progress is derived data and must be correctable

**Evidence:** [F3](01-introduction-and-goals.md) promises automatic PRs, estimated 1RM, and benchmark history without correction rules.

**Before M4:** define eligible lifts, estimation formula and rep range, units and rounding, benchmark version/equivalence, and which records are excluded. Specify recomputation after edits, deletion, and event replay; demonstrate rebuilding progress from retained source workouts. Oura charts show association, not evidence that recovery caused a result.

### R8 — Accepted infrastructure adds cost before it proves value

**Evidence:** [ADRs 0003–0006](../adr/README.md) choose multiple toolchains, pgvector, and RabbitMQ; [constraints](02-architecture-constraints.md) specify a solo part-time developer.

**Recommendation:** preserve these choices, stage their implementation, and distinguish installed components from used capabilities. Include the accepted local containers as scaffolding arrives, but do not invent consumers or embeddings. Movement aliases can be specified before deciding how embeddings help. The first agent-framework ADR should compare a simple validated provider call with framework options rather than assume orchestration is required. If removing an accepted component is later desired, propose a superseding ADR.

### R9 — Documentation needs to distinguish intent from implementation

**Evidence:** vision says initial decisions are resolved while strategy lists open technical decisions. C4 represents the planned full system, includes future broker consumers, and omits privacy from the core description. [ADR-0011](../adr/0011-git-workflow-and-versioning.md) retains the historical Kiro path; development instructions now adapt its branch prefix for Codex. No Git repository or executable checks were present at review time.

**Recommendation:** clarify the vision status without changing product choices; label C4 as a target view until implementation exists; add actual deployment/building-block views with M0/M1. Keep accepted ADR history intact and identify the current workflow location from the documentation entry points. Record the branch naming adaptation formally when the workflow is next reviewed. Complete arc42 incrementally, not as a prerequisite to every line of code.

## Resolution order

1. Agree the proposed milestones and first-demo boundary.
2. Resolve R1's initial examples and R2's authentication decision; choose web tooling and CI approach with targeted current documentation research.
3. Specify R3/R4 for the first personal logging slice; implement M0 then M1.
4. Resolve R5 before AI; R6 before gyms; R7 before progress; remaining provider/deployment questions when their milestone approaches.

The user owns product scope and acceptance of ADRs. Codex prepares options, specifications, implementation, and verification evidence. Each feature specification should reference the relevant review IDs and record how they were resolved.
